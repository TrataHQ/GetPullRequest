Opening a pull request is the final act in the GPR pipeline. Once your agent session completes and every verification command exits cleanly, GPR pushes the feature branch to your repository and opens a PR automatically. The PR includes the agent's commits, a generated description built from your task context, and a link back to the originating Jira or Linear issue—so reviewers have everything they need without any manual write-up from you.

## What Triggers a PR

GPR opens a PR when **all three** of the following conditions are true:

1. The agent session reached `completing` state (the agent signalled it was done).
2. All workspace verification commands exited with code `0`.
3. At least one new commit exists on the feature branch that is not yet on the base branch.

If verification fails, GPR stops before pushing and notifies you instead. No broken code ever reaches your remote repository automatically.

<Info>
  If you want to review the diff before the PR opens, you can enable **Manual PR approval** in workspace settings. GPR will run verification, show you a diff preview, and wait for your go-ahead.
</Info>

## What the PR Contains

### Branch and commits

GPR names feature branches using a predictable pattern:

```
gpr/<task-id>/<short-slug>
# e.g. gpr/TASK-42/add-rate-limiting-to-api-export
```

All commits the agent made during the session are included on this branch. GPR does not squash them by default, so reviewers can follow the agent's reasoning commit by commit. You can enable squash mode in workspace settings if you prefer a single commit per PR.

### PR description

GPR generates the PR description by combining your task description, a summary of the agent's changes, and metadata. If you've configured a PR template in the workspace, GPR populates it with the following values:

| Placeholder | Example value |
|---|---|
| `{{task_title}}` | `Add rate limiting to /api/export endpoint` |
| `{{task_description}}` | Full text of the task description you wrote. |
| `{{agent_name}}` | `Claude Code` |
| `{{source_issue_url}}` | `https://yourco.atlassian.net/browse/ENG-1234` |
| `{{verification_summary}}` | `4 checks passed (lint, typecheck, test, build)` |

A typical generated PR description looks like this:

```markdown
## Summary
Add rate limiting to the `/api/export` endpoint to prevent abuse.
Returns HTTP 429 with a `Retry-After` header when a user exceeds 10 req/min.

## Changes
- Added `src/middleware/rateLimitExport.ts` with per-user sliding window logic
- Modified `src/routes/export.ts` to apply the middleware
- Added `tests/middleware/rateLimitExport.test.ts` (3 tests, all passing)

## Linked issue
https://yourco.atlassian.net/browse/ENG-1234

## Verification
4 checks passed: lint · typecheck · test · build

---
*Opened automatically by [GPR](https://getpullrequest.com) using Claude Code.*
```

### Labels and reviewers

GPR can apply labels and request reviewers automatically. Configure these in workspace settings:

- **Labels** — a static list of label names to apply to every PR from this workspace (e.g. `gpr-generated`, `needs-review`).
- **Reviewers** — a list of GitHub/GitLab usernames to request review from, or `CODEOWNERS` to use your repository's code ownership rules.

## Opening a PR Manually

If you prefer to control when the PR opens, disable automatic PR creation in workspace settings and use the CLI or app:

```bash
# Open a PR for a completed, verified task
gpr pr open TASK-42

# Preview the PR description before opening
gpr pr preview TASK-42

# Open with a custom title (overrides the generated title)
gpr pr open TASK-42 --title "feat(api): rate limit /api/export to 10 req/min"
```

## Linking Back to Jira and Linear

When a task originates from Jira or Linear, GPR writes the PR URL back to the source issue automatically after the PR is opened. In Jira, this appears as a development link in the issue's sidebar. In Linear, it appears as a linked PR in the issue detail.

You can also configure GPR to **transition the Jira issue** to a new status when the PR opens—for example, moving it from "In Development" to "In Review" automatically.

```bash
# Configure the Jira transition for a workspace
gpr workspaces update api-service \
  --jira-on-pr-open "In Review"

# Or for Linear, set the target state
gpr workspaces update api-service \
  --linear-on-pr-open "In Review"
```

## PR Lifecycle After Opening

GPR monitors the PR after it's opened and reflects status changes back into the task.

| PR event | Task state change |
|---|---|
| PR opened | Task moves to `review_ready`. |
| Review requested changes | Task stays `review_ready`; you receive a notification. |
| PR approved | No automatic action; you merge manually or enable auto-merge. |
| PR merged | Task moves to `done`; Jira/Linear issue is transitioned if configured. |
| PR closed without merging | Task moves to `cancelled`; you receive a notification. |

<Tip>
  Enable **auto-merge** in your GitHub or GitLab repository settings alongside GPR's workflow. Once your CI passes and a reviewer approves, the PR merges without further manual action—completing the fully automated loop from Jira issue to merged code.
</Tip>

## Reviewing and Iterating on an Open PR

If a code reviewer requests changes, you have two options:

**Option 1 — Let the agent address the feedback**

Leave a comment on the PR or send a message to a new task. Create a follow-up task linked to the same branch and let the agent make the requested changes.

```bash
# Create a follow-up task targeting the existing PR branch
gpr tasks create \
  --title "Address PR review feedback on TASK-42" \
  --workspace api-service \
  --base-branch gpr/TASK-42/add-rate-limiting-to-api-export \
  --description "Reviewer asked: use a token bucket instead of sliding window. See comment: <link>"
```

**Option 2 — Fix it manually**

Check out the branch, make your changes, push, and the PR updates in place.

```bash
git checkout gpr/TASK-42/add-rate-limiting-to-api-export
# ... make changes ...
git commit -m "fix: switch to token bucket per review feedback"
git push origin gpr/TASK-42/add-rate-limiting-to-api-export
```

## Viewing All Open GPR Pull Requests

The **Pull Requests** page in the GPR app lists every PR opened by GPR across all your workspaces, along with its review status and the task it came from.

```bash
# List all open PRs created by GPR
gpr pr list

# Filter by workspace
gpr pr list --workspace api-service

# Filter by status
gpr pr list --status open --review-state changes_requested
```
