GPR connects your project management tools, AI coding agents, and version control into a single automated pipeline. When you assign a task to GPR—from Jira, Linear, Slack, or directly in the app—it picks up the context, spins up an agent session on your local machine, verifies the result in your real dev environment, and opens a pull request. You stay in control at every step and can monitor or intervene from anywhere.

## The Four Stages

Every piece of work moves through the same four stages: **Task → Agent Session → Verification → Pull Request**. Understanding this pipeline helps you configure GPR correctly and troubleshoot when something needs your attention.

```text
┌─────────────────────────────────────────────────────────────────┐
│                        GPR Pipeline                             │
│                                                                 │
│  ┌──────────┐    ┌───────────────┐    ┌────────────┐    ┌────┐ │
│  │   Task   │───▶│ Agent Session │───▶│Verification│───▶│ PR │ │
│  │          │    │               │    │            │    │    │ │
│  │ Jira /   │    │ Claude Code / │    │ Tests /    │    │ GH │ │
│  │ Linear / │    │ Codex /       │    │ Lint /     │    │ GL │ │
│  │ Slack /  │    │ Cursor /      │    │ Build      │    │    │ │
│  │ Manual   │    │ ACP Agent     │    │            │    │    │ │
│  └──────────┘    └───────────────┘    └────────────┘    └────┘ │
│                          │                                      │
│                   Runs on your                                  │
│                   local Machine                                 │
└─────────────────────────────────────────────────────────────────┘
```

## Stage 1 — Task

A Task is the unit of work. It carries everything the agent needs: a description, the target repository, the base branch, and any linked Jira or Linear issue. Tasks can be created automatically when you move a Jira issue to a configured column, triggered by a Slack message, or created manually with the CLI:

```bash
gpr task create
```

Tasks move through a defined lifecycle—`pending`, `assigned`, `running`, `verifying`, `pr_open`, `merged`, or `failed`—so you always know exactly where work stands.

[Learn more about Tasks →](/how-gpr-works/tasks)

## Stage 2 — Agent Session

Once a task is ready, GPR routes it to a registered **Machine**—a local development computer you've enrolled with `gpr connect machine`—and starts an **Agent Session**. The session launches your chosen AI coding agent (Claude Code, Codex, Cursor, or any ACP-compatible agent) in the workspace's repository directory, passing it the task description and context. The agent works autonomously, committing changes as it goes.

You can watch the session's output in real time, send messages to guide the agent, pause it, or cancel it at any point from the GPR mobile app or web dashboard.

[Learn more about Agent Sessions →](/how-gpr-works/agent-sessions)

## Stage 3 — Verification

Before GPR touches your remote repository, it runs a verification step inside the same local environment the agent used. Verification can include your test suite, linters, type checks, and build commands—configured per workspace. If any check fails, the task moves to `failed` state and you receive a notification so you can decide whether to retry, intervene manually, or discard the changes.

This step means broken code never reaches your repository automatically.

## Stage 4 — Pull Request

When verification passes, GPR opens a pull request on GitHub or GitLab. The PR includes the agent's commits, a generated description that summarises the changes, and a link back to the originating Jira or Linear issue. Reviewers get full context without any manual write-up from you. Use `gpr pr review` to inspect or approve open PRs from the CLI.

[Learn more about Pull Requests →](/how-gpr-works/pull-requests)
