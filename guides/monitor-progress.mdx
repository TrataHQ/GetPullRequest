Once you've assigned a task, GPR gives you several ways to follow along without being chained to a terminal. You can watch the session unfold command by command in the CLI, receive Slack messages at key milestones, or check a live progress view in the mobile app between meetings. This page explains what to look for at each stage and how to act when something looks off.

## Session stages

Every agent session moves through the same lifecycle:

| Stage | What's happening |
|---|---|
| `queued` | Task is waiting for the machine to come online or finish a prior session |
| `preparing` | GPR is checking out the branch, installing dependencies, and handing the task to the agent |
| `running` | The agent is actively reading files, writing code, and running tests |
| `verifying` | GPR is running your configured verification steps (lint, tests, build) |
| `opening_pr` | The agent is committing changes and GPR is opening the pull request |
| `done` | A PR is open and ready for your review |
| `failed` | The session ended with an error—see [Handle Task Failures](/guides/handle-task-failures) |

<Tip>
Most tasks reach `done` in 5–20 minutes depending on complexity and agent model. Large refactors across many files may take longer.
</Tip>

## Monitor with the CLI

<Steps>

### Check the current status

```bash
gpr task status TASK-123
```

```
Task:     TASK-123 — Add retry logic to payment processor
Status:   running
Stage:    running (agent writing code)
Agent:    claude-code
Machine:  macbook-pro
Session:  sess_a1b2c3
Started:  8 minutes ago
PR:       not yet opened
```

### Stream live logs

To tail the agent's output in real time—every file read, every shell command, every test run—attach to the session log stream:

```bash
gpr session logs sess_a1b2c3 --follow
```

Press `Ctrl+C` to stop tailing without affecting the session.

<Note>
Log lines prefixed with `[agent]` come from the AI model's tool calls. Lines prefixed with `[gpr]` come from the GPR orchestrator itself (branch setup, verification steps, PR creation).
</Note>

### Watch verification output

When the session enters the `verifying` stage, GPR runs your configured checks. Stream verification output separately to see test results as they arrive:

```bash
gpr session verify-logs sess_a1b2c3 --follow
```

```
[gpr] Running verification: npm test
[gpr] PASS src/payments/processor.test.ts (12 tests)
[gpr] PASS src/payments/retry.test.ts (8 tests)
[gpr] All checks passed. Proceeding to open PR.
```

### Poll for completion

If you'd rather not stream logs, poll until the session reaches a terminal state:

```bash
gpr task wait TASK-123
```

This command blocks and exits with code `0` when a PR is opened, or code `1` if the session fails—useful for scripting GPR into CI pipelines.

</Steps>

## Monitor via Slack

If you've connected GPR to a Slack workspace, the GPR bot posts a message in your configured channel at three key moments:

1. **Session started** — Posted when the agent begins working. Includes the task title, agent, and a link to the session.
2. **Verification passed** — Posted when all checks pass and GPR is about to open the PR.
3. **PR opened** — Posted with a direct link to the pull request for your review.

<Note>
To configure which Slack channel receives notifications, run `gpr config set notifications.slack.channel #your-channel`. To limit notifications to a single task, use `gpr task notify TASK-123 --slack @your-username` to send updates as a DM.
</Note>

The Slack message for an opened PR looks like this:

```
✅ GPR — PR opened for TASK-123
Add retry logic to payment processor

PR #214 · macbook-pro · claude-code · 3 files changed
https://github.com/your-org/your-repo/pull/214
```

You can react with ✅ to acknowledge or 🔁 to trigger a re-run directly from Slack (requires the GPR Slack app with write permissions).

## Monitor in the mobile app

<Steps>

### Open the task detail

Tap **Tasks** in the bottom navigation bar, then tap **TASK-123** to open its detail view. The status badge at the top updates live—no need to pull to refresh.

### Read the progress timeline

Scroll down to the **Session Timeline**. Each stage appears as a row with a timestamp and a short description of what happened:

```
✔ queued         10:02 AM   Task received by macbook-pro
✔ preparing      10:02 AM   Branch checked out, deps installed
● running        10:04 AM   Agent writing code  ← live indicator
  verifying      —
  opening_pr     —
```

A spinning indicator next to the current stage shows the session is active.

### View streaming logs on mobile

Tap **View Logs** on the task detail screen to open a scrollable, auto-updating log view. Tap **Pause** to stop auto-scroll so you can read a specific section.

<Tip>
Long-press any log line to copy it. This is useful for pasting an error message into a search engine or into a follow-up task description.
</Tip>

</Steps>

## What to watch for

### During `preparing`

- A hang longer than two minutes usually means a dependency install failed. Check logs for `npm ERR!` or similar package manager errors.
- A `branch conflict` error means the base branch has changed since GPR cloned it. Re-assign the task to pick up the latest commits.

### During `running`

- Log lines showing repeated file edits on the same file may indicate the agent is stuck in a loop. If this persists for more than five minutes, cancel and re-assign with a clearer task description.
- Watch for `[agent] tool_error` lines—these mean the agent attempted an action (like running a command) that failed. A few are normal; many in a row suggest the environment needs attention.

### During `verifying`

- Test failures here are expected to surface before a PR is opened. GPR will mark the session `failed` and report which tests failed. See [Handle Task Failures](/guides/handle-task-failures).

<Warning>
If the machine running the session loses network connectivity or is put to sleep, the session pauses and resumes automatically when the connection is restored. If it doesn't resume within 10 minutes, run `gpr task retry TASK-123` to start a new session.
</Warning>
