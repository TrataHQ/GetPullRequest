GPR is designed around a clear boundary: your source code and credentials live on your machine, and GPR's cloud handles only the lightweight coordination signals needed to route tasks and surface results. This page makes that boundary explicit—listing every category of data that crosses the network and everything that stays local—along with the specific network requirements for running the GPR daemon.

## What Travels to GPR's Cloud

The GPR daemon sends a small, well-defined set of metadata to GPR's cloud services. None of this data includes source code, file contents, or secrets.

### Task Metadata

When you assign a task to an agent, GPR's cloud stores a task record containing:

| Field | Example | Purpose |
|---|---|---|
| Task ID | `task_01hw3k…` | Unique identifier for routing and lookup |
| Task title | "Fix login timeout bug" | Display in dashboard and mobile app |
| Source issue reference | `PROJ-412` (Jira) | Link back to the originating issue |
| Assigned agent type | `claude-code` | Determines which agent binary to launch |
| Target repository name | `acme/api` | Identifies which local repo to work in |
| Assigned-to user ID | `usr_9f2a…` | Routes the task to the correct daemon |
| Created-at timestamp | `2025-06-10T14:32:00Z` | Ordering and audit trail |

<Note>
  The task title and issue reference come from your issue tracker (Jira, Linear). They are the same strings you see in your Jira board—not generated by GPR and not derived from your source code.
</Note>

### Status and Progress Events

As the agent works, the daemon streams a sequence of status events to GPR's cloud. These events power the real-time progress view in your dashboard and mobile app.

| Event Type | Example Payload | What Is NOT Included |
|---|---|---|
| `task.started` | `{ taskId, startedAt }` | No file paths, no code |
| `step.update` | `{ taskId, step: "running tests", stepIndex: 3 }` | No test output, no stdout |
| `verification.result` | `{ taskId, passed: true, failedChecks: [] }` | No compiler output, no log content |
| `task.failed` | `{ taskId, errorCategory: "test_failure" }` | No stack traces, no file diffs |
| `task.completed` | `{ taskId, completedAt, prUrl }` | No diff, no commit SHAs beyond what GitHub exposes publicly |

Step descriptions (like "running tests" or "fixing lint errors") are high-level labels generated by the agent framework. They describe what the agent is doing in general terms, not what files it is touching or what code it is writing.

### Pull Request and Merge Request Links

When the agent successfully opens a PR or MR, the daemon sends the URL to GPR's cloud so it can be displayed in your dashboard, posted to Slack, and surfaced in the mobile app. GPR stores the URL only—not the diff, not the commit messages, and not any comments.

### Authentication Tokens (Short-Lived, Scoped)

When the daemon connects to GPR's cloud, it authenticates using a short-lived JWT issued at daemon startup. This token identifies your user account and is rotated automatically every 24 hours. Your GitHub, GitLab, Jira, or Slack credentials are never sent to GPR's cloud.

## What Stays on Your Machine

The following categories of data never leave your local environment under any circumstances.

| Data Category | Why It Stays Local |
|---|---|
| Source code files | Agents read and modify files directly; no upload step exists in the daemon |
| File diffs and patches | Diffs are applied locally and pushed to GitHub/GitLab directly from your machine |
| Compiler output and build logs | Logs may contain secrets or PII; GPR only receives a pass/fail signal |
| Test output and stack traces | Same reason as build logs |
| `.env` files and secrets | The daemon explicitly excludes credential files from any telemetry |
| SSH keys and git credentials | Used by the local git process; never read by the daemon |
| Third-party API keys | Stored in your local keychain or `.env`; the daemon has no keychain-read permission |
| IDE configuration | Not relevant to task execution; never accessed |

<Note>
  If a test log or compiler output happens to contain a secret (for example, a leaked API key printed by a failing test), that output remains on your machine. Only a generic `test_failure` error category reaches GPR's cloud.
</Note>

## How Credentials Are Handled Locally

GPR uses your operating system's native secret store to persist any credentials the daemon needs between restarts:

- **macOS**: Keychain
- **Linux**: `libsecret` / GNOME Keyring (or an encrypted flat file if no keyring is available)
- **Windows**: Windows Credential Manager

Credentials are never written to `~/.gpr/config` or any other plain-text file on disk. If you uninstall the GPR daemon, your OS keychain entries are removed as part of the uninstallation.

## Network Requirements

The GPR daemon requires outbound HTTPS (port 443) access to a small set of GPR-operated hostnames. It does not require inbound connections, does not open listening ports on your machine, and does not use any protocol other than HTTPS and WSS (WebSocket over TLS).

### Required Hostnames

| Hostname | Protocol | Purpose |
|---|---|---|
| `api.getpr.dev` | HTTPS / WSS | Task assignment, status events, authentication |
| `app.getpr.dev` | HTTPS | Dashboard and mobile app backend |
| `updates.getpr.dev` | HTTPS | Daemon auto-update checks |

<Info>
  All three hostnames resolve to GPR-operated infrastructure. No traffic is routed through third-party CDNs that would have access to message content.
</Info>

### Connections Your Agent Makes Directly

In addition to GPR's own hostnames, the agent process makes direct outbound connections as part of normal development work. These connections go directly from your machine to the target service—they do not pass through GPR's cloud:

| Connection | Purpose |
|---|---|
| `github.com` / `gitlab.com` | `git push` to create feature branches and open PRs |
| Your Jira or Linear instance | Reading issue details (via the daemon's local Jira/Linear client) |
| Package registry (npm, crates.io, PyPI, etc.) | Installing dependencies during build/test |

### Firewall and Proxy Configuration

If your environment uses an HTTP proxy or requires allowlisting outbound destinations, add the three GPR hostnames above to your allowlist. The daemon respects the standard `HTTPS_PROXY` and `NO_PROXY` environment variables.

For air-gapped or highly restricted environments, contact [security@getpr.dev](mailto:security@getpr.dev) to discuss on-premises deployment options.

---

## Encryption in Transit and at Rest

All communication between the daemon and GPR's cloud uses TLS 1.2 or higher. GPR enforces HSTS on all endpoints and does not support plaintext fallback. Task metadata stored in GPR's cloud database is encrypted at rest using AES-256.
