Security questions deserve direct answers. This page addresses the most common concerns developers and security teams raise about GPR, covering everything from code storage and employee access to key management and offline behavior. If you have a question that is not answered here, reach out to [security@getpr.dev](mailto:security@getpr.dev).

<AccordionGroup>

  <Accordion title="Does GPR store my source code?">
    **No.** GPR never receives your source code, and therefore never stores it.

    AI coding agents run as processes on your local machine, inside the GPR daemon. They read and modify files directly in your local file system. When changes are ready, the agent pushes a branch directly from your machine to GitHub or GitLab using your existing git credentials—without routing the diff through GPR's cloud.

    The only things GPR's cloud stores are lightweight task records: a task ID, a title sourced from your Jira or Linear issue, status events like "tests passed," and the pull request URL once a PR is opened. None of these records contain file contents, diffs, or commit messages.

    For a full breakdown of what travels to GPR's cloud versus what stays local, see [Data & Connectivity](/security/data-and-connectivity).
  </Accordion>

  <Accordion title="Can GPR employees see my code?">
    **No.** Because GPR's cloud never receives your source code, GPR employees have no technical path to view it—there is nothing to query in a database, no object storage bucket, and no log pipeline where code might appear.

    The data that does exist in GPR's cloud (task metadata, status events, PR URLs) is access-controlled through standard role-based policies. Access to production data by GPR employees requires a formal approval process and is logged for audit purposes.

    If you are evaluating GPR for an enterprise deployment and require a formal data processing agreement or security questionnaire response, contact [security@getpr.dev](mailto:security@getpr.dev).
  </Accordion>

  <Accordion title="What happens if I revoke GPR's access to GitHub or Jira?">
    Revoking an integration immediately stops GPR from using that service.

    **For GitHub/GitLab:** New tasks that require opening pull requests will fail at the branch-push step. The agent will still run locally but will report an authorization error instead of opening a PR. Any PRs already opened remain open on GitHub/GitLab—revoking GPR's access does not close or modify existing PRs.

    **For Jira/Linear:** GPR can no longer fetch issue details or update issue status. Existing tasks in progress will complete but issue transitions and PR-link comments will not be posted.

    **For Slack:** GPR will stop posting status updates to your configured channels. Existing messages are not deleted.

    To fully disconnect a service, revoke access in both places:
    1. **GPR dashboard** → Settings → Integrations → Disconnect.
    2. **The third-party service** (GitHub OAuth Apps, Atlassian API tokens, Slack apps) to ensure the credential itself is invalidated.

    <Note>
      Revoking access in GPR's dashboard alone stops GPR from using the credential. Revoking it on the third-party side invalidates the credential entirely, even if it were somehow exfiltrated.
    </Note>
  </Accordion>

  <Accordion title="How are API keys and credentials stored?">
    GPR stores credentials in your operating system's native secret store—never in plain text on disk or in GPR's cloud.

    | Platform | Storage Mechanism |
    |---|---|
    | macOS | Keychain |
    | Linux | `libsecret` / GNOME Keyring |
    | Windows | Windows Credential Manager |

    When the GPR daemon authenticates with GPR's cloud, it uses a short-lived JWT (valid for 24 hours) rather than a long-lived API key. Your GitHub, GitLab, Jira, Linear, and Slack credentials are loaded from the OS keychain at the moment they are needed and are not held in memory beyond the duration of the operation.

    If no OS keyring is available on your Linux system, the daemon falls back to an encrypted flat file stored at `~/.gpr/secrets.enc`, using a key derived from your system's machine ID. This is less secure than a proper keyring; we recommend installing and enabling `gnome-keyring` or `kwallet` for production use.

    <Tip>
      You can verify which credentials GPR has stored by running `gprd credentials list` in your terminal. This command lists the services with stored credentials without revealing the credential values.
    </Tip>
  </Accordion>

  <Accordion title="Is communication between the daemon and GPR's cloud encrypted?">
    **Yes, always.** The GPR daemon communicates with GPR's cloud exclusively over TLS 1.2 or higher. There is no plaintext fallback, and GPR enforces HSTS on all endpoints.

    Specifically:
    - Task assignment and status events use a **WebSocket over TLS (WSS)** connection to `api.getpr.dev`.
    - Authentication and configuration calls use standard **HTTPS** to the same hostname.
    - Daemon update checks use **HTTPS** to `updates.getpr.dev`.

    TLS certificates are issued by a publicly trusted CA and are rotated before expiry. Certificate pinning is available for enterprise deployments that require it.

    Data stored in GPR's cloud database (task metadata, status events, PR URLs) is encrypted at rest using AES-256.
  </Accordion>

  <Accordion title="What if my machine is offline while a task is running?">
    Tasks continue running locally even if your internet connection drops. The GPR daemon buffers status events in a local queue and flushes them to GPR's cloud once connectivity is restored. You will see the full task timeline in your dashboard as soon as you are back online.

    If the daemon loses its connection to GPR's cloud *before* a task has been assigned, the task stays in a "pending" state in GPR's cloud until the daemon reconnects—at which point the task is delivered and begins running.

    The only operations that require an active connection are:
    - **Receiving a new task assignment** from GPR's cloud.
    - **Posting the PR URL** back to GPR's cloud after the agent opens a pull request.
    - **Pushing a branch** to GitHub or GitLab (this is a direct connection from your machine to the git host, not through GPR).

    If your machine goes offline after a task has started but before the branch push, the agent will complete its local work and the daemon will retry the push and status update when connectivity returns.

    <Info>
      GPR is designed for developers who work from laptops on intermittent connections. The daemon's offline-resilient buffering means a brief outage—a flaky Wi-Fi connection, a VPN reconnect—will not cause a task to be lost or duplicated.
    </Info>
  </Accordion>

  <Accordion title="Does GPR use my code to train AI models?">
    **No.** GPR does not send your source code to any AI model provider on your behalf, and it does not use any data from your environment to train or fine-tune models.

    The AI coding agents (Claude Code, Codex, Cursor, and ACP-compatible agents) run as local processes on your machine. Any inference calls those agents make go directly from your machine to the model provider's API using your own API keys—they do not pass through GPR's cloud. GPR has no visibility into the content of those inference calls.

    Your agreements with model providers (Anthropic, OpenAI, etc.) govern how those providers handle the prompts and context your agent sends. Review each provider's data usage policy for details.
  </Accordion>

  <Accordion title="What data does GPR log, and how long is it retained?">
    GPR's cloud retains task metadata (task IDs, titles, status events, PR URLs) for **90 days** by default. After 90 days, task records are automatically deleted.

    GPR's infrastructure logs (access logs, error logs) are retained for **30 days** and are used solely for debugging and reliability purposes. These logs contain IP addresses and request metadata—not task content.

    You can delete your account and all associated data at any time from **Settings → Account → Delete Account**. Deletion is permanent and completed within 30 days (to allow for backup rotation cycles).

    Enterprise plans can negotiate custom retention periods and data residency requirements.
  </Accordion>

  <Accordion title="Is GPR SOC 2 or ISO 27001 certified?">
    GPR is currently pursuing SOC 2 Type II certification. If you need a copy of our current security posture documentation, a completed security questionnaire, or our data processing agreement (DPA), contact [security@getpr.dev](mailto:security@getpr.dev) and we will respond within two business days.
  </Accordion>

  <Accordion title="What should I do if I suspect a security issue?">
    If you discover a vulnerability in GPR or believe your account has been compromised, contact us immediately at [security@getpr.dev](mailto:security@getpr.dev).

    For verified vulnerabilities, GPR operates a responsible disclosure program. We ask that you give us a reasonable window (90 days) to address issues before public disclosure, and we commit to acknowledging reports within 48 hours and providing a resolution timeline within 7 days.

    If your machine or a credential stored on it has been compromised:
    1. Revoke all GPR integrations from **Settings → Integrations**.
    2. Rotate the compromised credentials directly in GitHub, GitLab, Atlassian, or Slack.
    3. Run `gprd credentials purge` on your local machine to clear all stored credentials from your OS keychain.
    4. Re-authenticate GPR from scratch once you have secured your environment.
  </Accordion>

</AccordionGroup>
